1.1  Background and Necessity for the Application 
 
Sound-event monitoring is important in manufacturing plants, public spaces, 
transportation facilities, commercial buildings, homes, farms, service cent ers, 
and security-sensitive environments. Critical sounds such as machinery faults, 
gunshots, glass breaking, alarms, panic screams, aggression, and calls for help 
may indicate equipment failure, accidents, vandalism, violence, emergencies, or 
threats requiring immediate attention. 
 
Traditional sound monitoring depends on people continuously listening to live 
audio or manually reviewing recordings after an event has occurred. This process 
is time-consuming and prone to missed sounds, delayed responses, inconsistent 
decisions, and fals e alarms, particularly in noisy or crowded environments. 
SonicSentinel AI aims to automate and improve this process through Python -
based Web development, audio processing, machine learning, Google Teachable 
Machine, and intelligent event-analysis techniques. 
 
The ‘SonicSentinel AI’ reduces the requirement for completely manual sound 
monitoring by automatically analyzing uploaded audio clips and live microphone 
input. The application detects sound events such as Machinery Fault, Glass 
Breaking, Alarm or Siren, Vehicle Horn, Animal Sound, Gunshot, Panic Scream, 
Aggression, Person Asking for Help, or Background Noise. 
 
The application generates confidence scores using a Python classification model 
and compares the result with a separately trained Google Teachable Machine 
audio model. It also evaluates audio quality, detects uncertain or overlapping 
sounds, assigns event severity, and generates alerts for critical events. The goal 
is to deliver an accurate, secure, responsive, and accessible solution that 
supports faster sound-event detection and informed decision-making.

1.2  Proposed Solution  
 
The proposed solution introduces an AI -powered, Web -based, and real -time 
sound-event detection application that helps users, security teams, maintenance 
personnel, and administrators identify important sounds accurately and 
efficiently. 
 
Users can either upload an audio clip or enable live microphone monitoring 
through the Web application. The application validates the audio, extracts file 
information, removes or reduces unwanted noise, divides the audio into fixed -
duration segments, and extracts meaningful acoustic features. 
 
The Python classification model analy zes the pre-processed audio and predicts 
the detected sound category. The same audio segment is independently analyzed 
using a separately trained Google Teachable Machine audio model. Both models 
generate confidence scores for all supported classes. 
 
The application compares the predicted categories and confidence scores 
produced by the two models. It also generates a waveform and spectrogram, 
evaluates recording quality, detects overlapping or uncertain sounds, applies 
event-specific rules, and generates alerts for critical events. 
 
The application must support the following mandatory sound categories: 
 
1. Machinery Fault 
2. Glass Breaking 
3. Alarm or Siren 
4. Vehicle Horn 
5. Animal Sound 
6. Gunshot 
7. Panic Scream 
8. Aggression or Violent Conflict 
9. Person Asking for Help 
10. Background Noise 
 
Teams may add optional categories such as: 
 
• Drone Sound 
• Drilling or Grinder Sound 
• Fireworks 
• Vehicle Backfire 
• Explosion 
• Door Impact 
• Graffiti Spray

1.3  Purpose of the Document 
 
This document outlines the development plan for the SonicSentinel AI  
application using audio processing, Artificial Intelligence, Machine Learning, and 
Google Teachable Machine. It ensures that stakeholders and developers have a 
common understanding of the project requirements, promotes effective 
communication, and provide s a structured roadmap for developing a reliable 
sound-event detection application. 
Key areas include identifying critical sounds in real time, reducing manual audio 
monitoring, generating confidence -based predictions, and comparing Python 
and Google Teachable Machine results. The application also provides timely 
alerts for events such as gunshots, glass breaking, panic screams, aggression, 
machinery faults, and calls for help. This document is intended for both 
stakeholders and developers. 
1.4  Scope of Project 
 
The scope of the project includes developing a complete Machine Learning 
pipeline for the SonicSentinel AI  application. The project aims to automate 
sound-event detection by analyzing uploaded audio clips and live microphone 
input using audio -processing and machine -learning techniques. It extracts 
acoustic features, generates waveform and spectrogram visualiza tions, and 
classifies sounds using Python and Google Teachable Machine models.  


--- PAGE 19 ---
 
 
© Aptech Limited 
The application compares confidence scores and identifies events such as 
machinery faults, glass breaking, alarms, vehicle horns, animal sounds, 
gunshots, panic screams, aggression, calls for help, and background noise. The 
application also generates severity -based alerts, routes uncertain results for 
manual review, and presents live detections, event history, and reports through 
a user-friendly Web interface. 
 
1.5  Constraints 
 
The project may face several constraints, such as variations in audio quality, 
background noise, recording distance, microphone type, and overlapping sound 
events. Application accuracy depends heavily on the size, balance, diversity, and 
reliability of the training dataset, as well as the available computational 
resources. Differences may also occur between the predictions and confidence 
scores generated by the Python model and Google Teachable Machine. Ensuring 
audio privacy, obtaining user consent for microphone access, and avoiding bias 
across different speakers, environments, and recording devices are also critical 
limitations to consider.

There are several non -functional requirements that should be fulfilled by the 
application. 
 
1. Performance: The application should process and classify an uploaded audio 
clip of up to 30 seconds within eight seconds under normal operating conditions. 
Live sound windows should produce a prediction within three seconds. 
2. Scalable: The application should store and manage at least 20,000 sound-event 
records and support multiple concurrent users without significant performance 
degradation. 
3. Usable: The application should provide an intuitive and user-friendly Web 
interface for normal users, reviewers, security operators, maintenance 
personnel, and administrators. 
4. Accuracy: Both models should target an overall test accuracy of at least 85% 
and a macro F1 -score of at least 0.80. Critical classes such as Gunshot, Glass 
Breaking, Panic Scream, Aggression, and Person Asking for Help should target 
a recall of at least 85%. 
5. Available: The application should remain operational during required 
monitoring and evaluation hours with at least 99% uptime. 
 
 
 
 
 
 
These are the bare minimum expectations from the project. It is a 
must to implement the FUNCTIONAL and NON-FUNCTIONAL 
requirements given in this SRS. 
 
Once they are complete, you can use your own creativity and 
imagination to add more features if required.
